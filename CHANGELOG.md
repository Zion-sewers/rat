## [Unreleased]

### Added
- Identity propagation (rat #70): the agent acts with the user's permissions, never a super-key — `PermissionScope` (one user, servers, tools, optional expiry; deny-by-default; unknown scope keys rejected), `CredentialHandle` + `IdentityVault` (per-user handles that are references, never keys; no shared/global credential API exists; revocation enforced live per call for a vault-bound context; vault file mode 0600 enforced on every save on POSIX (best-effort on Windows, which has no POSIX permission bits)), `IdentityContext` (bound scope + handle + REQUIRED vault — a context whose vault never issued its handle is refused at bind time; one-way `user-<hash>` correlation token — a truncated unsalted hash, reversible with the user list, never a secret; raw user id never in any log). Enforced in the gateway (identity check before the trust check; audit events `identity_denied` / `identity_expired` / `credential_refused`; tool list filtered to the scope; the gateway re-validates the handle at bind) and the lifecycle (`begin_task` refuses out-of-scope servers before spawning anything; teardown and task-end audit events carry the identity token); live consumers are `mcp-guard gateway --identity scope.json` and `mcp-guard delegate --identity scope.json` (admission control: the contract's tools must be inside the delegating user's scope, refused before the junior starts). Authentication itself (OAuth / JWT / mTLS) stays a deployment concern; the library enforces the issued scope, it does not authenticate the user — a locally authored scope file is self-asserted, not authenticated. Identity is opt-in at the CLI: without `--identity` the gateway keeps its legacy declared-trust behavior and delegation's ceiling is the contract alone; making identity mandatory is a breaking change that needs a re-scope decision. The CLI's vault is ephemeral and in-process, so there is no cross-process revocation source in the shipped CLI session
- Memory poisoning defenses (rat #71, MPBench threat model): untrusted input must never become trusted memory — `_MemoryWriteGate` (sensitive-pattern gate on every write: SSN, Luhn-gated payment cards (13–19 digit runs, grouped or contiguous), PEM private-key blocks, `AKIA...` / `sk-...` shapes (gateway shapes plus the gate's own word-boundaried `sk-` shape at 10+ characters); refusals name only the pattern kind, never the value; email/phone not refused), `MemoryNamespace` (auth-bound (org, user, kind) namespaces — semantic / episodic / procedural / profile — the user half is a vault-issued `IdentityContext`, never a client-side string; the key carries the one-way audit token, never the raw user id; a caller cannot address another user's namespace through any `MemoryService` API), `MemoryService` (the single choke point and the ONLY public write path: constructed with the deployment's trusted vault — contexts from any other vault are refused — live identity re-validation, TRUSTED writes require the deployment-issued `memory.write_trusted` capability in the caller's scope, gate receipt bound to namespace key + content hash + provenance and HMAC-tagged with a per-gate secret the gate alone holds, receipt-checked store that refuses hand-built and cross-gate receipts; the gate, store, and receipt are module-private and the service constructs its own — no public bypass, the mutation test reaches the store's private `_write_raw` through the service's private store only). Trust is provenance, not content: `recall_trusted` returns only TRUSTED-provenance entries, so untrusted tool output never returns as trusted context; `write_tool_output` forces UNTRUSTED for tool results and a TRUSTED claim with a tool source is refused, so the quarantine does not depend on the caller labeling the poison correctly (remaining boundary, stated plainly: `source` is caller-declared, so a caller that HOLDS the trusted-write capability and lies about origin defeats the check — the capability is the authentication, and the deployment must issue it only to operator identities). `MPBENCH_SCENARIOS` (5 executable scenarios: 2 instruction poisons quarantined, 3 secret poisons refused) plus mutation tests proving each defense load-bearing (gate for secrets, service path + provenance label for instruction poison); audit log records write decisions, never content. Store is in-memory only; entries serialize through the `MemoryEntry` mapping contract, which preserves the provenance label across restarts. Authentication stays a deployment concern
- Central MCP gateway (`mcp-guard gateway`, rat #66): trust-level enforcement in the request path (a low-trust caller can never trigger a high-trust read), pre-model PII tokenization with detokenization on later calls, and an audit log of events, never content (the one exception, added by rat #69: the approver name on an `escalation_approved` event, which records as a per-session `[APPROVER_n]` token, never verbatim and never resolvable back to the value)
- MCP least-privilege lifecycle (rat #68): servers off by default, narrow per-task enablement via `ServerRegistry`, and post-task teardown verified against the live process (`TeardownReport`; a surviving server fails the teardown instead of reporting clean). The `gateway` subcommand is the production consumer: the session is one task, and `--servers` enables multi-server tasks via stdin control lines
- Rule-of-two escalation + PII pseudonymization before any output (rat #69): on gateway calls, a HIGH-trust mutating tool on untrusted input escalates and is denied before any send without a second approval (`SecondApproval`, audited; the approver name records as a per-session `[APPROVER_n]` token, the whole field pseudonymized, never verbatim and never resolvable back to the value) — but the same caller can attach its own approval or declare its input trusted, so the control stops accidental omission and creates an audit trail, it does not enforce two distinct humans; the harness must obtain approval from a distinct principal out of band; the fuzzer is exempt from the rule (it does not run through the gateway). Fuzz reports (table/JSON/SARIF) are scrubbed at the emit boundary, before any preview truncation, emit-only and unconditional (no opt-out), so no raw structured PII of the detected classes reaches any report (names and bare 9-digit national IDs excepted); the detector also matches +972 Israeli mobiles and uses a bounded email pattern plus a per-family pre-filter (1M-char runs covered by regression tests with a 10s bound). Gateway CLI lines print the tokenized tool name, never the raw name — including the annotated tool list, scrubbed at its print site — and rejected trust values are never echoed back

## [0.1.0] - 2026-06-03

### Added
- Initial release of mcp-guard
- Stdio transport with JSON-RPC 2.0 handshake
- Schema-aware adversarial payload generation (5 probe types)
- Dynamic fuzzing engine with SAFE / FINDING / CRASH classification
- Static schema scanner with shell injection, SSRF, and missing-schema rules
- CLI with `fuzz` and `scan` subcommands
- Output formats: table, JSON, SARIF
- Zero runtime dependencies (Python 3.11+ stdlib only)
